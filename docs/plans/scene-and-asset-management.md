# Feature: Scene and Asset Management

## 0. How to use this doc

Standalone implementation spec — treat it as the only context you have. For exhaustive facts about the current codebase state, read `docs/codebase-map.md` first. This feature has one hard prerequisite:

- `docs/plans/raytracing-in-a-weekend.md` — this feature adds save/load to that feature's already-built `RaytraceSceneEditor` panel; it does not redesign that panel's live sphere-editing UI.

It also extends infrastructure from `docs/plans/imgui-display.md` (the main menu bar, and the docking-branch ImGui vendored there — ImGuizmo, §2.8 below, needs to be paired with the same branch) and unblocks — but does not itself implement — work deferred in `docs/plans/compute-pipeline-raytracing.md` §2.8 (that doc explicitly deferred *sampling* an HDR environment map in its `crt_shade.comp` shader to "whenever a scene/asset-management feature exists"; this doc makes the HDR resource loadable and available, but writing that GLSL sampling code remains that other doc's concern, to be revisited there once this feature exists). This doc's gizmo system (§2.8) is also a prerequisite for `docs/plans/simulation-domain.md`'s simulation plane, once that's written.

**Scope boundary — read this before touching `RaytraceSceneEditor`'s glTF object browser**: `docs/plans/raytracing-in-a-weekend.md` already added glTF mesh-node rows to the scene browser, where "selecting one shows nothing" is explicitly a placeholder for a *different*, still-unplanned future feature (triangle/BVH mesh tracing). This doc does not change that placeholder or make mesh objects raytraceable — this doc is purely about loading, saving, and managing scene *data* (glTF files, sphere scenes, HDR environment maps), not rendering capability.

## 1. Feature goal

Let the user load an arbitrary glTF scene at runtime (not just the one hardcoded at startup), load an HDR image to use as environment lighting later, save/load the raytracer's sphere scene (`RaytraceSceneEditor`, `docs/plans/raytracing-in-a-weekend.md`) to and from disk — using glTF's own `extras` extensibility mechanism as the sphere-scene file format, so a saved sphere scene is a real, valid (if minimal) `.gltf` file that other glTF tools can open without erroring, just without seeing anything meaningful in it — and give any editable scene object (spheres today, other object types like the future simulation plane later) a shared 3D gizmo for directly manipulating its transform in the viewport, opt-in per object via an explicit "Edit Transform" action rather than always-on.

## 2. Architecture decisions made and WHY

### 2.1 Sphere scenes are saved as minimal, valid `.gltf` files using the `extras` field — not a custom format, not a custom extension

glTF 2.0's `extras` field is a standard, spec-defined mechanism present on most glTF objects (scenes, nodes, meshes, etc.) for arbitrary application-specific JSON data — the spec requires compliant readers to preserve but not error on unrecognized `extras` content. This is a better fit than a formal custom `extensions` entry (which implies registering an extension name and, conventionally, some schema expectations) for data that's purely this application's own concern and never meant to be interpreted by other tools.

**Verified this is actually buildable with the vendored `fastgltf`** (not assumed): `fastgltf/include/fastgltf/core.hpp` exposes `ExtrasParseCallback`/`setExtrasParseCallback()` (fires during parsing with a `simdjson::dom::object*` for each glTF entity's `extras`, indexed by object + `Category`) and `ExtrasWriteCallback`/`setExtrasWriteCallback()` (supplies an `optional<std::string>` of JSON text to embed when exporting), plus a real `fastgltf::Exporter`/`FileExporter` class with `writeGltfJson(const Asset&, ...)`. So both directions — reading `extras` back out, and writing them into a freshly-exported file — are real, existing library capabilities, not something to build from scratch.

**Concretely**: "Save Sphere Scene" constructs a minimal in-memory `fastgltf::Asset` (required `asset.version = "2.0"` field, one empty `Scene`) and calls `Exporter::writeGltfJson()` with an extras-write callback that returns a hand-built JSON string (see §2.2) for that scene. "Load Sphere Scene" parses the file with `loadGltf()`'s existing `fastgltf::Parser` machinery plus `setExtrasParseCallback()`, extracts the scene's `extras` JSON object, and populates `RaytraceSceneEditor`'s sphere list from it. Save files get a genuine `.gltf` extension, since that's honestly what they are — a valid (if nearly content-free) glTF document.

**Where the extras attach**: the file's single `Scene` (index 0), not the top-level `asset` object. `fastgltf`'s callback signature takes an `objectIndex`, which fits indexed, array-based entities like scenes cleanly; whether the top-level singular `asset` object participates in the same callback mechanism the same way is unclear from the header alone and wasn't verified further — Scene-level extras is the safer default to build against first (see §8).

### 2.2 No new JSON library — `simdjson` (via `fastgltf`) for reading, hand-built strings (via `fmt`) for writing

Reading: `fastgltf` already vendors and links `simdjson` internally, and exposes it directly in its own public API (`ExtrasParseCallback`'s `simdjson::dom::object*` parameter) — so navigating the parsed sphere-list JSON on load uses `simdjson`'s DOM API directly, no separate parsing library needed.

Writing: `ExtrasWriteCallback` wants a raw JSON string back, not a structured builder object — but the sphere-list payload has a small, entirely self-controlled, fixed shape (an array of spheres, each with position/radius/inlined material fields), so hand-formatting that string via `fmt::format` (already a project dependency, per `CLAUDE.md`) is entirely sufficient. A general-purpose JSON-writing library was considered and rejected — the project isn't writing arbitrary/nested/user-defined JSON, just one small fixed-shape array, and adding a dependency for that would be solving a problem this codebase doesn't have.

**Materials are inlined per-sphere, not deduplicated via a shared reference table.** Each saved sphere entry carries its own complete material data (type + parameters) directly, even if several spheres happen to share identical material settings. This was chosen over a separate indexed material list with per-sphere references because it keeps the read/write logic and the JSON shape simpler (no reference-resolution step), at the cost of some redundancy that's irrelevant at this scene's scale (a handful of spheres).

**Include a `"version": 1` field in the JSON payload from the start**, so a future change to the sphere/material schema (e.g. a new material type) has something to branch on when reading an older save file, rather than needing to guess a file's age from its contents.

### 2.3 HDR environment maps are loaded independently of the sphere-scene save format

HDR (`.hdr`, Radiance format) loading is a separate, standalone action — not bundled into the glTF+extras sphere-scene mechanism from §2.1. glTF's `images` array only accepts `image/jpeg`/`image/png` per spec; embedding a non-standard HDR payload into a glTF file would need its own custom extension and defeats the "stays a valid, boring glTF file" property that makes the `extras` approach clean. Instead, an HDR file is loaded directly as a standalone asset via `stbi_loadf()`/`stbi_is_hdr()` — confirmed already present in the vendored `stb_image.h` (`STBIDEF float *stbi_loadf(...)`, `STBIDEF int stbi_is_hdr(...)`) — no new dependency needed, and `.hdr`-only support (no `.exr`) was chosen specifically because it's what the existing dependency already provides; OpenEXR support would need a new library (e.g. `tinyexr`) for a format this project doesn't currently have any other reason to parse.

The loaded HDR becomes a single `AllocatedImage` resource owned by `VulkanEngine` (e.g. `m_environmentMap`), replacing any previously-loaded one (old resource destroyed via the existing `destroyImage()` before the new one is created, mirroring `LoadedGLTF::clearAll()`'s existing cleanup pattern). **Actually sampling this resource in a shader (the deferred HDR-on-miss work from `docs/plans/compute-pipeline-raytracing.md` §2.8) is out of scope here** — this feature's job ends at "the image is loaded, valid, and available on `VulkanEngine`."

### 2.4 Fixing a real bug found during planning: `createImage()`'s hardcoded 4-bytes-per-pixel upload size

Verified directly in `src/vk_engine.cpp:717`: `VulkanEngine::createImage(void* data, ...)` computes its staging-buffer size as `size.depth * size.width * size.height * 4` — correct today only because its one existing caller (`load_image()` in `vk_loader.cpp`, for glTF textures) always uses `VK_FORMAT_R8G8B8A8_UNORM` (4 bytes/pixel). HDR data loaded via `stbi_loadf()` is 4 floats/pixel — 16 bytes/pixel, not 4 — so calling the existing function as-is with HDR data would under-size the staging buffer and corrupt or truncate the upload.

**Fix**: replace the hardcoded `* 4` with a small format-to-bytes-per-pixel lookup (covering at minimum `VK_FORMAT_R8G8B8A8_UNORM` = 4 and `VK_FORMAT_R32G32B32A32_SFLOAT` = 16, the two formats this codebase will actually upload through this path). This is a strict generalization, not a behavior change for the existing caller — `load_image()`'s RGBA8 uploads compute the same size as before. Framed as a bug fix bundled into this feature (since this feature is what first needs a non-RGBA8 upload through this path), not a speculative refactor.

### 2.5 File access: a plain path text field, no file-picker dialog

Loading a glTF scene, an HDR map, or a saved sphere scene all use a simple `ImGui::InputText` for the file path plus a Load/Save button — no native OS file dialog and no custom in-engine file browser widget. This was chosen as the simplest thing that works: no new dependency (a native dialog would need one — confirmed no such library is currently linked into VkGuide's build, even though SDL, which has one, happens to sit unused in the shared `CPPLibraries` folder), and no meaningful new UI code to write and maintain. A nicer picker can replace this later without touching anything else in this design, since it only affects how a path string gets produced, not what happens once one exists.

### 2.6 Single active glTF scene — loading replaces it

Loading a new glTF file clears `m_loadedScenes` (`vk_engine.h:190`) and loads just the new one, generalizing today's hardcoded single-scene-at-init behavior (`m_loadedScenes["structure"] = ...`, `vk_engine.cpp:54`) into something triggerable at runtime rather than adding true multi-scene composition. This avoids two problems a multi-scene model would introduce: name collisions between scenes sharing node/mesh names, and deciding where a newly-added second scene gets positioned relative to whatever's already loaded — neither has an obvious answer, and multi-scene composition wasn't something this feature needs to solve.

### 2.7 File-loading errors are recoverable, not hard aborts

`checkVkResult`/`vkbErr` (`src/vk_types.h:115-129`) hard-abort on any Vulkan/vk-bootstrap failure — appropriate for internal engine invariants that should never fail in a working build. A bad user-supplied file path (typo, wrong format, missing file) is different: it's an expected, recoverable user-input error at a real system boundary, not an internal invariant violation. Loading failures in this feature (glTF parse failure, HDR load failure, malformed sphere-scene JSON) should report an error (e.g. a short-lived ImGui message/toast near the input field) and leave existing state untouched, rather than aborting the whole application. This is a deliberate, narrow exception to the codebase's otherwise-uniform hard-abort convention, justified specifically because this is user-facing file I/O, not an internal precondition.

### 2.8 Generic gizmo-based transform editing, shared across object types — not object-specific UI code

Add **ImGuizmo** (new vendored dependency, `../CPPLibraries/ImGuizmo`, added the same way as the other sibling libraries in the root `CMakeLists.txt` — the standard 3D-manipulation-widget library for Dear ImGui, and the natural pairing once the docking branch is already in use per `docs/plans/imgui-display.md` §2.1) so the user can directly drag-manipulate an editable object's transform in the 3D viewport, rather than only through numeric sliders.

**Design**: a single, object-agnostic `TransformGizmo` (owned once by `VulkanEngine`, `m_transformGizmo`) tracks at most one "active" edit target at a time — a raw `glm::mat4*` pointing directly at whichever object's transform is currently being edited, plus which `ImGuizmo::OPERATION` (translate/rotate/scale) applies. Any object type that wants gizmo support adds an "Edit Transform" button to its own existing UI panel; clicking it calls `m_transformGizmo.beginEditing(matrixPtr, operation)`, which becomes the new active target and deactivates whatever was previously active. Every frame that a target is active, `TransformGizmo` calls `ImGuizmo::Manipulate()` against the raster camera's current view/projection and that `glm::mat4*`, which ImGuizmo mutates directly when dragged — no polling or event plumbing needed beyond that.

**Why a raw matrix pointer, not a shared virtual interface**: object types in this codebase represent their own transforms differently — a sphere is `center + radius` (`docs/plans/raytracing-in-a-weekend.md`), a future simulation plane (`docs/plans/simulation-domain.md`) is position + orientation + extent, a glTF `Node` already has a `localTransform`/`worldTransform` `glm::mat4`. Rather than forcing every object type to implement a shared virtual interface just to be gizmo-editable, each object type owns its own small conversion to/from a plain `glm::mat4` (e.g. sphere: translation = center, uniform scale = radius, identity rotation) — `TransformGizmo` itself stays a simple, reusable, object-agnostic utility operating on nothing but a matrix pointer. This matches the low-ceremony, non-virtual style this codebase's utility types generally use (`DescriptorLayoutBuilder`, `vkutil::transition_image`, `DisplayRegistry`) — `hittable`/`material`'s virtual dispatch is specific to the raytracer's own need for polymorphic material *behavior*, not a general pattern to extend here.

**Exclusive, opt-in activation — not always-on, not tied to list selection.** Per explicit direction, the gizmo only appears once the user clicks a "Transform"/"Edit" button on a specific object's own panel; it is not automatically bound to whatever row happens to be selected in `RaytraceSceneEditor`'s object browser, and only one object's gizmo is ever active at a time. This avoids gizmo widgets cluttering the viewport by default and avoids ambiguity about which object a visible gizmo currently controls.

**`RaytraceSceneEditor` gains an "Edit Transform" button per sphere** (`docs/plans/raytracing-in-a-weekend.md`), alongside — not replacing — its existing position/radius sliders. Both coexist: sliders for precise numeric entry, the gizmo for direct manipulation; neither redesigns the other.

**Interaction with camera controls**: ImGuizmo dragging and the camera's mouse-look/WASD both want input, and will fight over it if not explicitly arbitrated. `docs/plans/imgui-display.md` §2.9 introduces exactly this arbitration — an explicit capture-mode boundary between "controlling the camera" and "interacting with the UI," entered by holding the right mouse button over the raster background. That entry trigger already checks `!ImGuizmo::IsOver() && !ImGuizmo::IsUsing()` before allowing capture, specifically so a click on or near an active gizmo handle is never mistaken for a camera-look request — this feature relies on that check existing (build `docs/plans/imgui-display.md` §2.9 first, or alongside this), rather than adding its own separate camera-suppression logic.

**Viewport rect**: `docs/plans/imgui-display.md` §2.2 established that the raster 3D scene is a full-screen background, not a dockable panel — there is no "viewport panel" whose content region would normally feed `ImGuizmo::SetRect()`. Set it to the full window/swapchain extent instead; ImGuizmo draws into the current ImGui draw list, which already renders on top of the blitted scene via the existing `drawImgui()` ordering (`docs/codebase-map.md` §1), so this should compose correctly, but is worth confirming visually once built since most ImGuizmo examples assume a dockable viewport panel rather than a full-screen background.

## 4. Implementation order and dependencies

Depends on `docs/plans/raytracing-in-a-weekend.md` being implemented (needs `RaytraceSceneEditor` to exist) and `docs/plans/imgui-display.md` (needs the main menu bar and the docking-branch ImGui to exist — ImGuizmo needs to be paired with the same branch).

1. **`createImage()` bug fix** (§2.4) — small, isolated, no dependency on anything else here. Verify existing glTF texture loading still works identically (no regression) before moving on.
2. **HDR loading** (§2.3) — `loadEnvironmentMap()` + File-menu entry. Verify by loading a real `.hdr` file and confirming `m_environmentMap` is populated with sane dimensions/format (no shader consumes it yet — that's fine, this step is purely "can the resource be loaded and held").
3. **Runtime glTF scene loading** (§2.6) — generalize the existing loader to be callable at runtime, wire the File-menu entry. Verify: load a different `.glb`/`.gltf` file at runtime and confirm the raster viewport and `RaytraceSceneEditor`'s object browser (`docs/plans/raytracing-in-a-weekend.md`) both correctly show the new scene's contents and no longer show the old one.
4. **`rt_scene_io.h/.cpp` — write path first.** Build the minimal `Asset`, wire the extras-write callback, save a sphere scene, and manually inspect the resulting `.gltf` file's JSON text to confirm it's well-formed and the extras payload looks right, before writing any read-back code.
5. **`rt_scene_io.h/.cpp` — read path.** Parse the file saved in step 4 back in, confirm the resulting sphere list matches what was saved (position/radius/material fields all round-trip correctly).
6. **Wire load/save into `RaytraceSceneEditor`'s panel** (§3) — buttons + path fields, calling into `rt_scene_io`. Verify end-to-end: edit spheres, save, clear/reset the editor, load the save back, confirm the scene is restored, and confirm the compute raytracer (if built) correctly detects this as a scene change and resets its accumulation (via the existing dirty-flag path, no new work needed there per §3's note).
7. **Error handling** (§2.7) — verify by deliberately pointing each load action at a bad path and confirming a clean error message appears rather than a crash.
8. **Vendor ImGuizmo, `src/vk_gizmo.h/.cpp`** (§2.8) — independent of everything above, can be built and smoke-tested in isolation first: wire `beginEditing()` to a scratch/throwaway matrix and confirm the gizmo appears, drags correctly, and `endEditing()`/switching targets behaves before touching `RaytraceSceneEditor` at all.
9. **Wire the "Edit Transform" button into `RaytraceSceneEditor`** (§2.8) — sphere↔matrix adapter, verify dragging the gizmo actually moves the sphere (and that the raytracer, if built, picks up the change via the same dirty-flag path saving/loading already relies on per step 6).
10. **Camera/gizmo input arbitration** (§2.8) — verify mouse-look doesn't fight with gizmo dragging near/over a gizmo handle.

## 5. Edge cases / traps identified during planning

- **The `createImage()` fix must not change behavior for existing callers** — `load_image()`'s glTF-texture uploads (`vk_loader.cpp:426` etc.) must compute the exact same buffer size as before (RGBA8 = 4 bytes/pixel); verify this explicitly, since a silent size miscalculation here would corrupt every glTF texture load, not just the new HDR path.
- **Whether `fastgltf`'s extras callback mechanism actually fires for the minimal single-`Scene`, effectively-empty `Asset` this feature constructs** hasn't been verified beyond confirming the callback types exist in the header — verify this concretely in step 4 of §4 before building anything downstream of it (see §8).
- **Scene-change reset must be triggered by *loading* a sphere scene, not just by manual edits.** If the load path bypasses `RaytraceSceneEditor`'s normal sphere-list-mutation code path (e.g. by directly poking a private member instead of going through the same setter manual edits use), the compute raytracer's dirty-flag-driven accumulation reset (`docs/plans/compute-pipeline-raytracing.md` §2.4/§2.6) would silently miss the change. Route the load path through the exact same mutation entry point manual editing already uses.
- **HDR resource lifetime**: loading a second HDR file must destroy the first via `destroyImage()` before creating the replacement, or it leaks GPU memory every time the user loads a different environment map.
- **glTF scene replacement must fully tear down the old scene** (`LoadedGLTF::clearAll()`'s existing pattern, `vk_loader.cpp:491-516`, already destroys buffers/images/samplers correctly) before the new one loads — confirm this happens when triggered at runtime, not just at shutdown, since it's never been exercised as a runtime operation before (only ever run once at init, then again at final `cleanup()`).
- **Format versioning** (§2.2): the `"version": 1` field is easy to forget to add on the very first implementation and expensive to retrofit later once save files exist in the wild (even if that "wild" is just this one user's own machine) — include it from the first working version, not as a follow-up.
- **Dangling gizmo target** (§2.8): if the object currently being edited is deleted (e.g. a sphere removed) while its gizmo is active, `TransformGizmo`'s `glm::mat4*` becomes a dangling pointer. Whatever code removes an editable object must call `m_transformGizmo.endEditing()` first if that object is the current target.
- **Gizmo mode per object type**: a sphere has no meaningful rotation (rotationally symmetric) — its adapter should probably only expose translate (and maybe uniform scale for radius), not all three `ImGuizmo::OPERATION` modes. This is a per-object-type decision each future gizmo consumer needs to make for itself, not something `TransformGizmo` should hardcode or restrict generically.
- **ImGuizmo + full-screen background scene** (§2.8): most ImGuizmo integration examples assume a dockable "viewport" panel providing a natural rect and hover/focus boundary; this project's full-screen-background scene (`docs/plans/imgui-display.md` §2.2) doesn't have one. Confirm `SetRect()` against the full window extent doesn't cause the gizmo to draw or accept input over other ImGui windows that happen to overlap it on screen.

## 6. Code patterns from the existing codebase to follow

- **glTF parsing setup**: `loadGltf()` (`vk_loader.cpp:177-401`) is the existing `fastgltf::Parser`/`GltfDataBuffer` setup pattern — `rt_scene_io.cpp`'s read path should reuse the same parser-construction shape, just adding `setExtrasParseCallback()` and not caring about meshes/materials/nodes at all.
- **GPU resource cleanup ordering**: `LoadedGLTF::clearAll()` (`vk_loader.cpp:491-516`) is the direct precedent for "destroy every owned GPU resource before replacing/discarding this object" — the same shape applies to swapping `m_environmentMap` and to runtime glTF scene replacement (§2.6).
- **Staging-buffer image upload**: `createImage(void* data, ...)` (`vk_engine.cpp:715-751`) is exactly the path `loadEnvironmentMap()` reuses (once fixed per §2.4) — no new upload mechanism needed, just a new caller with a different format.
- **Menu bar extension**: `docs/plans/imgui-display.md`'s `DisplayRegistry::drawWindowsMenu()`/`ImGui::BeginMainMenuBar()` — this feature's "File" menu is a sibling addition to the same menu bar, not a separate UI surface.
- **`fmt` usage**: already a project dependency (per `CLAUDE.md`); use it for building the sphere-list JSON string in the write path (§2.2) rather than raw string concatenation.
- **Non-virtual, object-agnostic utility shape**: `DescriptorLayoutBuilder`/`vkutil::transition_image`/`DisplayRegistry` (`docs/plans/imgui-display.md`) are the precedent `TransformGizmo` follows (§2.8) — a small reusable type operating on primitive data (here, a raw `glm::mat4*`), not a virtual interface every consumer must implement.
- **Sibling-dependency vendoring**: `../CPPLibraries/imgui` (already amended for the docking branch, `docs/plans/imgui-display.md` §2.1) is the precedent for how `../CPPLibraries/ImGuizmo` gets added — same `add_subdirectory` pattern in the root `CMakeLists.txt`.

## 7. What NOT to do (alternatives rejected and why)

- **Do not** invent a custom (non-glTF) file format or a formal registered glTF `extensions` entry for sphere scenes (§2.1) — `extras` is the simpler, standard-fit mechanism for exactly this kind of private, non-interoperable application data, and it's already confirmed usable via `fastgltf`.
- **Do not** add a JSON library dependency (§2.2) — reading goes through `simdjson` (already available via `fastgltf`), writing is simple enough to hand-format with `fmt` given the payload's small, fixed, fully-self-controlled shape.
- **Do not** embed HDR image data inside the glTF save file (§2.3) — glTF's `images` array doesn't support HDR formats without a custom extension, and doing so would compromise the "stays a boring, valid glTF file" property that's the whole point of the `extras` approach. Keep HDR loading as its own independent, standalone-file action.
- **Do not** add a native file-dialog dependency or build a custom file-browser widget in this pass (§2.5) — a plain path text field is sufficient and keeps this feature's scope to "load/save works," not "load/save has a polished picker."
- **Do not** build true multi-scene composition (§2.6) — name collisions and relative-placement questions have no obvious answer and weren't asked for; single-active-scene-replace is simpler and sufficient.
- **Do not** hard-abort on a bad file path the way the rest of the codebase hard-aborts on internal Vulkan failures (§2.7) — this is a deliberate, narrow, justified exception for user-facing file I/O specifically, not a general loosening of the codebase's error-handling convention.
- **Do not** deduplicate materials across saved spheres via a shared reference table (§2.2) — inlining per-sphere is simpler and the redundancy is irrelevant at this scene's scale.
- **Do not** build a click-to-select-in-3D-viewport picking system (§2.8) — per explicit direction, gizmo activation is via an explicit "Transform"/"Edit" button on an object's own panel, not by clicking the object itself in the 3D view. No ray-picking-against-scene-geometry system is needed for this feature.
- **Do not** give every object type a shared virtual "IEditable" interface (§2.8) — a raw `glm::mat4*` target plus a per-object-type conversion is simpler and avoids forcing unrelated object representations (sphere center+radius, node matrices, future plane transforms) through one artificial shape.
- **Do not** allow more than one object's gizmo to be active simultaneously (§2.8) — exclusive activation was explicit direction, and avoids ambiguity about which object a visible gizmo controls.

## 8. Open questions / things to verify before starting

1. **Whether `fastgltf`'s extras callbacks work cleanly against a minimal, near-empty `Asset`/`Scene`** (§2.1, §5) — the header confirms the callback types exist, but constructing a minimal valid `Asset` via `fastgltf`'s C++ object-model API and round-tripping `extras` through `Exporter::writeGltfJson()` + `setExtrasParseCallback()` wasn't traced through in full API detail during planning. Verify this concretely and early (§4 step 4) — if Scene-level extras turns out to be awkward through this API, Asset-level `extras` (the top-level `asset` object, always present, no index) is the fallback to try next.
2. **Exact JSON shape for the sphere-list payload** (§2.2) — this doc specifies *that* it's an array of spheres with inlined material fields and a version number, but not the precise field names/types; reasonable to finalize while implementing step 4 of §4, informed by whatever `RaytraceSceneEditor`'s actual sphere/material struct fields end up being once that feature is built.
3. **Where save files and HDR assets are expected to live** — no fixed directory convention was specified beyond the general `m_rootPath`-relative pattern (`shaders/`) the rest of the project already uses; a sensible default (e.g. pre-filling the path text field with `scenes/` or similar) is a small implementation-time UX decision, not an architectural one.
4. **Whether a loaded environment map should get a preview thumbnail via `docs/plans/imgui-display.md`'s `DisplayRegistry`** — an easy, cheap addition once both features exist, but not required for this feature's goal; worth a quick check-in once implementing rather than deciding now.
5. **Should glTF node transforms also become gizmo-editable** (§2.8), letting the user reposition loaded mesh objects in the raster scene directly? Not explicitly asked for — the explicit examples given were spheres and the future simulation plane — and `RaytraceSceneEditor`'s glTF browser rows are currently a deliberate non-interactive placeholder for a *different* reason (deferred mesh-tracing capability, not general transform editing, per this doc's own scope-boundary note). Worth a direct check-in before building rather than assuming either way.
6. **ImGuizmo version/compatibility with whichever docking-branch ImGui snapshot ends up vendored** (`docs/plans/imgui-display.md` §8) — not verified during planning.
7. **Whether gizmo mode (translate/rotate/scale) should ever be user-selectable** (e.g. keyboard shortcuts matching common 3D tools) versus fixed per object type as this doc currently assumes (§5) — no need for this to be resolved now; revisit if/when a second gizmo-consumer (the simulation plane) makes the pattern clearer.
